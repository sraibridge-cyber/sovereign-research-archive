# Audit: sovereign-research-archive, 2026-11-18

End-to-end audit of the repository on `main` (after PR #1), checked against `docs/ARCHITECTURE.md`, the README and CONTRIBUTING, and the S.R.A. role described in *The four-layer architecture* (Drive, Nov 10): research memory, history, provenance and retrieval, with rejected material preserved rather than destroyed.

Evidence labels: **VERIFIED (ran)** means the behaviour was reproduced by running code; **VERIFIED (read)** means it follows from the code with no run needed; **NOT TESTED** means no run was possible here; **OPEN** means not changed in this PR.

## Summary

The host-side pipeline did not work end to end: ingestion wrote no documents, the build's seal check could not fail, the seals could not be recomputed, and the kernel's on-device SHA3-512 produced wrong hashes. All four are fixed in this PR and covered by tests. The Android build itself is still unverified because the CI workflow on `main` is invalid and needs to be replaced by hand.

## What was run

- Host end to end: sample corpus -> `ingest.py` -> `--verify` -> `build_apk.sh` steps 1 to 3 (passes), then with a deleted seal (build stops at step 2).
- `tools/test_ingest.py`: 15 tests, 14 pass, 1 skipped because a PDF library is installed in the test environment.
- `src/test_ghost.js` 31/31; `src/test_sha3_fallback.js` 266/266.
- `src/research_index.js` through a better-sqlite3 stand-in over `node:sqlite`: its archive passes `ingest.py --verify`, so the Node and Python seal formats agree.
- Schema check against my reproduction of the DDL Room generates for the entities: fresh, migrated (old `merkle_seals` without `doc_sha3`) and Node-built archives all match.

## Not run

Gradle build and lint, APK install, Rhino execution, FTS5 on Android, Room `createFromAsset` on a device, a real Drive export, PyMuPDF and python-docx extraction.
